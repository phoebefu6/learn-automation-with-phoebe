Triggers, actions and the data between

Last session ended with one sentence: when X happens, do Y with Z. Tonight each of those letters gets a mechanism. X is a trigger, and it either gets told the instant something happens or has to keep asking. Z is the data, and it travels between steps as items, bundles or mapped fields, losing pieces at every step that reshapes it. Y is the action, and it can only use what survived the trip. You will run n8n on your own machine, import a real five-node workflow, and follow one order from webhook to text message, watching exactly where its event id disappears.

Part 0

Where we start

Every no-code tool draws a workflow as boxes joined by lines, and the lines look like nothing. They are where most of the surprises live. A trigger that polls can miss nothing and still fire twice after you pause it. A step that fetches a customer record can hand the next step the customer and throw away the order. None of this shows on the canvas; all of it shows in the output panel of each step, which is the one screen worth learning to read tonight.

Part 1 · covers instant and polling triggers

How a trigger finds out

5 min live

There are only two ways for a workflow to learn that something happened. Either the app calls you, sending one HTTP request to a webhook URL the moment the event occurs, or you call the app, asking on a timer whether anything is new. The first is instant and trusts the sender. The second is late by up to one interval and has to remember what it has already seen. Both can hand you the same event twice, for different reasons.

LiveInstant or polling, and how to tell3 min▶

Instant (a webhook). You give the app a URL. When the event happens, the app sends one HTTP POST to it with the event in the body. Nothing runs on a timer and nothing is compared: whatever arrives is the event. Zapier marks these triggers "Instant" in its picker; in n8n it is the Webhook node, which gives you a test URL and a production URL; in Make it is a webhook module.

Polling. Your tool asks the app on a schedule, "what is in the list now?", and works out what is new by comparing ids. Zapier's platform docs say that by default "the field with the key id is used as the primary key" for this. Late by up to one interval, and every check costs something somewhere: Make's help defines an operation as "a single module run to process data or check for new data", so a trigger check counts once even when there is nothing new. Make now bills in credits (since 27 August; 1 operation equals 1 credit for non-AI apps), so read "operation" there as "credit".

How to tell for your own app. Look for the words "webhook", "instant" or "notification URL" in the app's settings or in the trigger picker. If all you can find is "new row", "new file" or "new email" with a check interval, it is polling. Homework 1 is exactly this.

Self-studyThe seen-list resets when you switch it off3 min▶

Zapier's deduplication docs describe the memory behind a polling trigger: when a Zap is turned on, it stores the ids it can currently see, so old items are not treated as new; on every later poll, any id not in that list is a new item and runs the Zap once. When the Zap is turned off, the list is cleared. Turn it back on and one poll fills the list again from whatever is there at that moment.

Two consequences follow, both practical. Items that arrive while the Zap is off are in the list the first poll stores, so they are treated as already seen rather than as new; if you need them processed, that is a manual replay, not a toggle. And the dedupe is only as good as the id field: if an app gives an edited record a fresh id, or two records the same one, the seen-list will run the edit as new or skip the second record. The rest of the platform behaves accordingly: Zapier's help article "How Zapier handles duplicate data in Zaps" (updated 29 May 2026) states plainly that "Instant triggers do not use deduplication because apps only send new data." That sentence is the claim Part 1's figure puts next to Stripe's.

The general lesson is wider than Zapier. Any memory a tool keeps on your behalf, a seen-list, a cursor, an idempotency key store, is state you did not write down, and pausing or rebuilding the workflow can reset it. Session 6 comes back to this as a maintenance item.

Real world

Two documents that disagree, both read at source. Zapier's help says instant triggers skip deduplication "because apps only send new data". Stripe's webhook docs say "Webhook endpoints might occasionally receive the same event more than once", retry failed deliveries for up to three days in live mode, and advise tracking the event ids you have processed. Both are honest about their own side: Zapier does not dedupe, and Stripe does resend. Put them together and an instant trigger from a sender like Stripe can run your workflow twice for one payment. Nothing in either tool removes the repeat for you; session 5 builds the guard, and homework 4 lets you watch your own tool do it.

Part 2 · covers items, bundles, fields

What travels between steps

5 min live

Between any two boxes on the canvas there is a small parcel of data. n8n calls it an item, Make calls it a bundle, Zapier shows it as the output fields of a step that you map into the next one. The parcel is rebuilt at every step that shapes or fetches something, and a step that fetches usually hands on only what it fetched. Below is one real order, evt_0002, as it actually looks after each of the five nodes in rung-1.json.

LiveWhat travels, and what gets dropped3 min▶

The webhook wraps. n8n's Webhook node puts the request's payload under body, next to headers, params and query. So the order's type is $json.body.type, not $json.type. The first expression most people write here returns nothing.

The Set node trims. "Shape the message" is a Set node with includeOtherFields off: it builds a new item with exactly three fields, event_id, customer_id and amount, and everything else, ts, type and the whole body wrapper, is not passed on. That is deliberate here: the next step needs a clean parcel. It also means any later step that wants the timestamp cannot have it.

The lookup replaces. "Look up customer" is an HTTP Request. Its output item is the CRM's answer, customer_id, phone and name, and nothing else. It does not merge the answer into the item it received. After it, event_id and amount are simply not in the item, and the send step needs both. A step that fetches is a step that replaces: treat every HTTP call that way until its output panel shows otherwise.

Self-studyItems, bundles and mapped fields across the three tools4 min▶

n8n. The n8n docs page on its data structure says "all data passed between nodes is an array of objects", each item wrapped in a json key. An array, because one node run can carry many items: a trigger that returns ten new rows hands ten items to the next node, and that node runs once per item. $json in an expression is the json of the item currently being processed.

Make. The same parcel is a bundle. A module receives bundles and outputs bundles; a search module that finds five records outputs five bundles, and every later module runs once per bundle, each run counting as an operation, now a credit. The bundle inspector after a run (the bubble over each module) is Make's version of n8n's output panel.

Zapier. You rarely see the parcel as one object. Each step publishes output fields, and in the next step you map them into inputs by picking "Step 1: Customer Email" from a list. The mechanism is the same, the presentation differs: a field you never mapped is not carried forward for you, and a field that a step did not output cannot be picked later.

ToolThe parcelWhere to read it after a run
n8nan array of items, each {json: {...}}the node's output panel (Table, JSON, Schema)
Makebundles, one module run per bundlethe bubble over each module in the run history

The habit that transfers: before wiring step N, open step N-1's output and check that every field step N needs is actually there.

Real world

The missing timestamp (a common pattern, constructed example). A shop adds a "received at" line to its confirmation text a month after launch. The builder maps ts in the send step and gets an empty value, because the Set node two steps earlier never kept it. The fix takes thirty seconds once you look at the Set node's output; finding it takes an afternoon if you only look at the send step. The lesson is the reading order: walk the output panels from the trigger forward, not from the broken step backward.

Part 3 · covers expressions and reaching back

Reaching past a step that replaced the item

5 min live

The send step needs the customer's phone, which is in the item in front of it, and the event id, which is not. The way out is to stop reading the current item and read an earlier node's item instead, by name. That is the whole of the expression language this workflow needs: one form for "here" and one for "back there".

LiveTwo expressions are enough for this workflow3 min▶

n8n expressions sit inside {{ }}, and a parameter that holds one starts with =. Every expression in rung-1.json is one of two forms.

Here: $json.field. The item the node is processing right now.

  • IF "Is it an order?": ={{ $json.body.type }} equals order
  • Set "Shape the message": event_id = ={{ $json.body.event_id }}, customer_id = ={{ $json.body.customer_id }}, amount = ={{ $json.body.amount }} (number)
  • Lookup URL: =http://127.0.0.1:8787/crm/customers/{{ $json.customer_id }}?event_id={{ $json.event_id }}
  • Send body: to = ={{ $json.phone }}

Back there: $('Node name').item.json.field. The matching item of an earlier node, by its name.

  • Send body: event_id = ={{ $('Shape the message').item.json.event_id }}
  • Send body: text = =Order {{ $('Shape the message').item.json.event_id }} confirmed, {{ $('Shape the message').item.json.amount }} paid. Thank you.

Notice the Set node reads $json.body.* (it is right after the webhook) and the lookup reads $json.customer_id (it is right after the Set). The same field has a different path depending on which node you are standing in. That is the item changing shape, made visible.

Self-studyWhen a reach-back breaks: renamed nodes2 min▶

A reach-back names a node in a string: $('Shape the message'). Rename that node to "Build SMS" and every expression that still says 'Shape the message' points at a node that no longer exists. Depending on the version and where the expression sits, the editor may update references for you or the run fails at the send step with an error about the referenced node. Do not rely on either; treat a node rename as a change to every node downstream of it.

Three practice habits make this cheap, none of them measured, all of them common sense. Name nodes for what they produce ("Shape the message", "Look up customer") on day one, so there is no reason to rename later. Before renaming, search the workflow JSON for the old name in quotes; every hit is an expression to check. After renaming, run one test event and read the output panel of every node after it, not only the last one.

Make and Zapier map fields by a step's position or id rather than by a free-text name, so this exact failure is mostly n8n's; their version is deleting or reordering a step that later steps mapped from.

Real world

GitHub gives you 10 seconds. GitHub's "Best practices for using webhooks" asks receivers to respond with a 2XX within 10 seconds, and lets you redeliver a missed delivery, which keeps the same X-GitHub-Delivery header. Two things follow for this workflow. The "Order webhook" node in rung-1.json is set to respond as soon as it receives the request, not after the lookup and the send finish, so a slow CRM never makes the sender think the delivery failed. And a redelivery is, by design, the same event a second time: the delivery id it carries is exactly the kind of key session 5 uses to make the repeat harmless.

Homework

Before session 3

30 min
  1. Name your own trigger type. For the candidate task from session 1, find out whether the app can call a webhook (instant) or only be checked on a schedule (polling). Write down which, and where in the app you found it.
  2. Write the item at each step. List the steps of your candidate and, under each, the fields that come out of it. Mark any step that fetches something, because it probably replaces the item rather than adding to it.
  3. Find one field that is dropped on the way. Pick a field the final action needs (an id, an amount, a timestamp) and trace it back. Is it still in the item when the action runs, or does the action have to reach back for it?
  4. Post the same test event twice to your tool (or to the n8n test URL from step 6) and note what happens. Two runs? One? Two messages in the mock's /log? Keep the note; session 5 starts from it.
Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Zapier says instant triggers do not deduplicate "because apps only send new data". Why can an instant trigger still run your workflow twice for one event?

Both sources are accurate about their own side. Zapier does not dedupe instant triggers; Stripe does resend, with retries for up to three days in live mode. Together they mean one payment can arrive twice. Session 5 builds the guard.

2 · In the send step after "Look up customer", $json.event_id comes back empty. Why, and what fixes it?

After the lookup the item is customer_id, phone and name, nothing else. $json reads that item. The reach-back reads the Set node's item, where event_id still lives. Option C would be right at the Set node, which is right after the webhook, and wrong here.

3 · A polling Zap is turned off for an afternoon and turned on again. What happens to its seen-id list?

Zapier's deduplication docs: ids are stored when a Zap is turned on and the list is cleared when it is turned off. Re-enabling re-initialises it from a poll. A toggle is not a replay; items that arrived while it was off need a deliberate one.
