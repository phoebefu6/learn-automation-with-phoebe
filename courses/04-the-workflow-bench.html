The workflow bench

Sessions 1 to 3 argued about what to automate and what it costs. Tonight a workflow runs. The same five-node n8n workflow you imported in session 2 processes one seeded day of 600 webhook events, 344 of them orders that should each produce exactly one text message. The day contains the four things that go wrong in real automations: a lookup that times out, a 500 error, a message that is sent but whose reply never arrives, and a provider that is down for half an hour. Four versions of the workflow run in front of you, from no retry to a dead-letter queue, and the page counts every text sent, every duplicate, every order lost and every run billed.

Part 0

Where we start

A bench holds everything still except the thing you are testing. The day is fixed: 600 events between 07:00 and 22:00, seed 1205, with every failure decided by a hash of the event, the step and the attempt number, so the same failure hits the same order on every replay. The workflow is real n8n JSON. What changes between rungs is three node settings and one header, and the bench reads them from the JSON rather than pretending.

Part 1 · covers what the bench runs and what can fail

One day, four ways to fail

6 min live

The workflow is the one from session 2. A webhook receives an event. An IF node lets only orders through. A Set node shapes the message. An HTTP Request looks the customer up in the CRM to get a phone number, and a second HTTP Request sends the text. Two of those five steps talk to another company's server, and those two are where every failure on the bench is injected.

LiveThe four failures, and the one that lies3 min▶

Timeout on the lookup (2% of tries). The CRM does not answer within the node's 10-second timeout. Nothing happened on the other side; trying again is safe.

500 errors (3% of tries at each HTTP step). The server says it failed before doing anything. On the SMS step, nothing was sent. Trying again is safe.

Sent, reply lost (4% of tries at the SMS step). The provider sends the text, then the response is lost on the way back. The workflow sees exactly what it sees for a timeout, and n8n reports it as a failure. The customer has the text. This is the one that lies: the run is red and the work is done. Trying again is not safe unless something tells the provider it is the same message.

The outage (13:00 to 13:30). Every send for an order that arrives in those thirty minutes gets a 503. Thirteen orders arrive in the window. Any number of retries seconds apart will hit the same closed door.

Self-studyWhat the runner implements, and how it was checked against real n8n3 min▶

The bench is a small workflow runner written for this page. It reads n8n's own JSON for five node types (webhook, IF, Set, HTTP Request, and the HTTP Request used as the dead-letter step) and implements the settings that matter here with n8n's semantics: retryOnFail, maxTries, waitBetweenTries and onError. The retry limits are n8n's own, read in its engine source (n8n-core 2.41.6, getRetryParams): max tries clamped between 2 and 5, default 3; wait between tries clamped to at most 5,000 ms. Expressions are limited to the two forms the workflows use, $json.field and $('Node name').item.json.field.

Before any number on this page was written, the same four workflows were imported into a real n8n 2.41.6 (Node 24) and run against a local copy of the mock endpoints for six events chosen to hit every failure path. All 24 runs matched the bench's prediction on run status, texts sent and dead-letter entries, and so did the two break-button runs. An independent Python implementation agrees with the browser on every count, for every rung, every failure switch and both store settings. The workflow files are rung-1, rung-2, rung-3 and rung-4.

LiveFinding 1: red is not lost, and green is not delivered2 min▶

On rung 1, 51 runs end red and 40 orders are lost. The other 11 red runs are lost replies: the provider sent the text and the workflow never heard back, so n8n marked the run failed. If someone "fixes" those 11 by replaying them from the executions list, 11 customers get a second text. The executions list tells you which runs failed; it does not tell you what happened on the other side. Only the receiver's log does.

The reverse is also true on rung 2: runs that end green include the 11 that sent twice. A green run means the workflow finished, not that the customer got exactly one message.

LiveFinding 2: retry everything trades losses for duplicates2 min▶

Turning Retry On Fail on for every HTTP step is the reflex fix, and it works on the failures it was meant for: losses fall from 40 to 13. But it also retries the step whose reply was lost, and nothing in the second request says "this is the same message". The provider sends it again. Eleven customers are texted twice.

The proof is the switch: with lost replies switched off, rung 2 has zero duplicates. The retry is not the problem. Retrying a step that has side effects, without an identity for the side effect, is. A lookup can be retried freely, because asking the CRM twice changes nothing; a send cannot.

LiveFinding 3: no retry setting reaches past an outage2 min▶

Rungs 2 and 3 both lose the same 13 orders: the ones that arrived during the outage. n8n caps a node's retries at 5 tries with at most 5 seconds between them, so the longest a node-level retry can wait is 20 seconds. The outage lasts 30 minutes. Raising the retry count would not help even if the cap allowed it; it would only hit the closed door faster. What reaches past an outage is a place to put the work and a later attempt: the dead-letter queue and its redrive.

Self-studyFinding 4: the same day costs three different shapes of money3 min▶

n8n bills per execution: 600 runs cost 600 units whether a run had one step or forty retries, so its cost per run stays at €0.0080 on every rung; only the 13 redrives add anything. Zapier bills per successful action: failed steps are free, so rung 1, where the most steps fail, uses the fewest tasks (621), and the dead-letter rung uses the most (714) because every parked event and every redrive succeeds at something. Make bills per module run, trigger included; the bench assumes a failed module run still uses a credit, because the Make pages read for this build do not say either way.

At 714 tasks a day, the Zapier version of this workflow needs about 21,000 tasks a month against a 750-task entry plan. The per-unit price shown is the entry plan divided by its tasks; at that volume a real bill sits on a much larger tier. Session 3 has the tier tables. The point the bench makes is the shape: on per-step billing, reliability costs units; on per-run billing, it mostly does not.

Part 3 · covers the break button

The key is a promise the receiver keeps

4 min live

An idempotency key looks like something the workflow does: it adds a header. It is really something the receiver does: it remembers the key and refuses to do the work twice. The break button leaves the workflow untouched and switches the receiver's memory off, and the duplicates come straight back.

LiveWhat "idempotent" has to mean for a step with side effects2 min▶

A step is idempotent when doing it twice leaves the world the same as doing it once. Reading is idempotent by nature. Sending a text, charging a card or creating a record is not, unless the receiver makes it so. Stripe's API is the textbook version: send an Idempotency-Key header and Stripe saves the result of the first request for that key, then returns the same result to any repeat. Your key choice matters: the bench uses the event id, because the event is the thing that must happen once. A random id generated fresh on every try would be a different key each time and protect nothing.

The break button is the test every idempotency claim should pass: switch off the store and the duplicates must reappear. If they do not, the bench was not measuring what you thought.

Self-studyWhen the receiver keeps no store2 min▶

Many APIs a no-code workflow calls have no idempotency key at all: a chat message, a spreadsheet row, most email sends. Then the store has to live on your side. Write "sent: evt_0101" somewhere durable after the send succeeds, and check it before sending. n8n's Remove Duplicates node can keep that memory across executions (operation "Remove Items Processed in Previous Executions"), and session 5 shows the trap in it: placed before the send, it marks the event seen before the send has succeeded, so a failed send that is redriven later is silently dropped. Either check before and mark after, or accept the receiver's memory where it exists.

Real world

Webhook senders deliver more than once on purpose. Stripe's webhook documentation says endpoints "might occasionally receive the same event more than once" and tells you to log the event ids you have processed; it retries undelivered events for up to three days. GitHub's webhook best practices ask for a 2XX within 10 seconds and note that a redelivery carries the same X-GitHub-Delivery header. Both are telling you the same thing the bench shows from the other side: delivery is at least once, so exactly once has to be built.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · On rung 1, 51 runs end red but only 40 orders are lost. What are the other 11?

A lost reply looks exactly like a timeout to the workflow. Red means the workflow did not hear success, not that nothing happened. Only the receiver's log can tell the two apart.

2 · Retry everything cuts losses from 40 to 13 and adds 11 duplicate texts. How does the bench prove where the duplicates come from?

Change one thing, watch one counter. The duplicates belong entirely to retries of a step with a side effect and no identity. Retrying the CRM lookup is harmless; retrying the send is not, until it carries a key.

3 · Rung 3 still loses 13 orders, all from the 13:00-13:30 outage. Why would raising the retries not save them?

Retries are for blips. Outages need a place to put the work and a second attempt after the door reopens. On rung 4 the 13 orders are parked, redriven at 23:30 and texted, and the key makes the redrive safe.
