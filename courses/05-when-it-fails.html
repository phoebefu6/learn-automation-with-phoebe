Part 0

Where we start

The bench gave you a ladder and a price for each rung. It did not give you the settings. A retry is three fields on a node. An idempotency key is one header whose value has to come from the right place. A dead-letter queue is an error output wired to one more step, plus somebody who reads what lands there. Each of those is small, and each has one way of being set up that looks right and quietly does the opposite. Tonight is about finding those traps before a customer does.

Part 1 · covers retries, backoff and jitter

Retry only what is safe

5 min live

A retry is a bet that the second try will see a different world from the first. For a read, the bet is free: looking a customer up twice changes nothing. For a write, the bet depends on a question the workflow usually cannot answer: did the first try already land? On the bench, with the "reply lost" failure switched off, retrying everything produced 0 duplicates. Switched on, it produced 11. Every one of them came from retrying a send whose reply never arrived.

LiveWhich steps may be retried3 min▶

Reads, freely. A lookup, a search, a "get the row" call returns the same thing twice and changes nothing on the other side. Retry it as often as the time budget allows. On the bench, the CRM lookup timing out or returning a 500 cost nothing once it was retried.

Writes, only with a key. A send, a create, a charge, a post to a channel: if the first try landed and only the reply was lost, the retry does it again. The workflow sees a timeout and cannot tell "never arrived" from "arrived, answer lost". Real n8n showed exactly this on rung 1: the run went red with "timeout of 10000ms exceeded" while the mock's log held one delivered message. Retry a write only when the receiver can recognise the repeat, which is what Part 2's key is for.

Writes with no key at all. Do not retry them automatically. Park the event (Part 3) and let a person check the receiving side before anything is sent again.

In n8n the three settings sit on each node's Settings tab: Retry On Fail, Max Tries and Wait Between Tries. Read in the engine source (n8n-core 2.41.6, getRetryParams), Max Tries is clamped to 2 to 5 (default 3) and the wait to at most 5,000 ms (default 1,000). The longest node-level retry window is therefore 4 waits of 5 seconds: 20 seconds.

Self-studyBackoff and jitter, and why n8n's node retry is not backoff4 min▶

Backoff means waiting longer after each failure: 1 second, then 2, then 4, up to a cap. A struggling server gets room to recover instead of a steady hammering. Jitter means not waiting exactly that long, but a random time below it. Without jitter, every client that failed at the same moment retries at the same moment, and the retries arrive as one more spike.

Marc Brooker's AWS Architecture Blog post (4 March 2015) compared the variants in a simulation. Full jitter, where the wait is a random value between 0 and the ceiling, had the lowest client work, and with 100 contending clients adding jitter cut the number of calls by more than half. The figure above is backoff.py running full jitter with a 60-second cap: the ceilings double, the actual waits do not, and the worst case before giving up is 123 seconds.

n8n's node retry is not backoff. Wait Between Tries is one fixed number, the same before every try, with no jitter and a ceiling of 5 seconds. That is fine for a blip. It is not a strategy for a provider that is down, because no setting on the node can wait longer than 20 seconds in total. Anything that has to outlast minutes or hours needs to leave the run and come back later: a dead-letter list and a redrive. Make's Retry error handler does schedule attempts minutes apart (reported, see the table below), and Zapier's Autoreplay replays an errored step on its own schedule, which its help page does not state.

Real world

Stripe backs off for three days. When your endpoint fails to accept a webhook, Stripe's documentation says it retries automatic delivery for up to three days in live mode, with exponential backoff. The same page warns that "Webhook endpoints might occasionally receive the same event more than once." Both halves are the lesson: the sender retries patiently over days, not seconds, and because it retries, the receiver has to recognise a repeat. Your workflow is the sender to the SMS provider and the receiver for Stripe at the same time.

Part 2 · covers idempotency keys and what to do without one

The key comes from the event

5 min live

An idempotency key is a name for one intended action, sent with every attempt at it. The receiver remembers the first result for that name and hands the same result back to any repeat, without doing the action again. It works only if two things hold: every retry of the same action carries the same key, and the receiver keeps a store of keys it has seen. On the bench, switching the store off on rung 4 put 13 duplicates straight back.

LiveWhere the key comes from3 min▶

From the event, never from the attempt. The key has to be the same on the first try, every retry and the 23:30 redrive. The event id is exactly that: it was decided before your workflow ran and it travels with the event. On rung 3 the send node's header is Idempotency-Key with the value $('Shape the message').item.json.event_id. Reaching back to "Shape the message" matters, because the lookup step replaced the item with the CRM's answer and the event id is no longer on it (session 2).

A fresh random id per try protects nothing. A key generated inside the step, a UUID or a timestamp, is new on every attempt, so the receiver sees a different name each time and does the action each time. The header is present, the code looks careful, and the duplicate rate is exactly that of rung 2.

When the receiving app has no key. Many APIs accept no idempotency header. Then keep your own "already sent" record: a sheet, a database row or a small store, keyed by event id. n8n's Remove Duplicates node can hold that record (operation "Remove Items Processed in Previous Executions", keep items where the value is new, history of 10,000 items by default, scoped to the node or the whole workflow). The trap is in the figure: placed before the send, it marks the event seen before the send has succeeded. A send that fails and is redriven later is then dropped as a repeat. Check before, mark after success. Your own record also cannot cover the lost-reply case completely: if the send landed and the reply did not, your record says "not sent". Only the receiver's own key closes that gap.

The same discipline at data-team scale, where whole pipeline tasks are retried and backfilled, belongs to Data Orchestration.

Self-studyProvider semantics differ: Stripe replays a stored 5003 min▶

Stripe's idempotent requests are the reference most people copy, and they hold three surprises. First, Stripe saves "the resulting status code and body of the first request made for any given idempotency key, regardless of whether it succeeds or fails". A repeat with the same key returns the same result, "including 500 errors". If the first try failed on Stripe's side once execution had begun, retrying with the same key gets the same failure back; it does not try again.

Second, keys may be pruned after at least 24 hours. A redrive the next day, or a manual replay a week later, can arrive after the key is gone, and then it is a new request. Third, keys can be up to 255 characters, and Stripe advises against putting personal data in them: an event id is a good key, a customer's email address is not.

The mock SMS endpoint behaves differently: it suppresses a repeat and answers duplicate-suppressed with the first message id. Neither is wrong. They are different contracts, and the only way to know which one you are calling is to read the provider's page for it before you rely on the key.

Real world

GitHub hands you the key. GitHub's webhook best-practices page says to answer within 10 seconds and to redeliver missed deliveries, and that a redelivery keeps the same X-GitHub-Delivery header. That header is a ready-made idempotency key for anything your workflow does on receipt: record it before you act on a delivery you have not seen, and a redelivered one becomes a no-op. The sender already decided the name of the action. Your job is to use it rather than invent a new one.

Part 3 · covers dead letters and alerts

Park it, then tell a person

5 min live

Some failures outlast every retry. During the bench's half-hour outage, rungs 2 and 3 lost the same 13 orders no matter how they retried. A dead-letter queue changes the question from "how long can this run wait?" to "where does the event go when it cannot wait any longer?" It goes to a list, it stays there with its id, and later, once the provider is back, it is sent through the same workflow again. Rung 4 did that at 23:30 and texted all 344.

LiveA dead-letter list someone reads3 min▶

The pattern is old and well documented. Amazon SQS describes a dead-letter queue as the place a source queue sends "messages that are not processed successfully". A setting called maxReceiveCount decides how many receives a message gets before it moves there. A redrive moves messages back to the source to be processed again. The documentation also advises that the dead-letter queue keep messages longer than the source queue, and it documents alarms on messages arriving there.

In n8n, rung 4 is two settings and one step. On both HTTP nodes, On Error is set to Continue (using error output), which gives the node a second output for items that failed after all their retries. Both error outputs go to Park in dead-letter queue, which posts the event id to a list. On the real n8n run, evt_0251, arriving in the outage, retried for about 10 seconds, ended with status success, last node "Park in dead-letter queue", 0 messages sent, and a dead-letter list of ["evt_0251"].

A list nobody reads is a slower way of losing the order. Three rules make it a queue rather than a graveyard: one named owner who checks it, an alert when it is not empty, and a redrive that sends parked events back through the same workflow, which is safe only because the key from Part 2 is on the send. How that owner works through it, step by step, is a runbook; the craft of writing one is in Data Reliability's runbooks session.

An alert someone can act on names five things: the event id, the step that failed, the error text, a link to the run, and the person who owns it. "Workflow failed" sent to a shared channel names none of them.

Self-studyError workflows versus error outputs3 min▶

n8n has two error mechanisms, and they catch different things. An error output is per node: the failed item leaves by a second wire and the run continues. An error workflow is per workflow: in Workflow Settings you name a separate workflow that must start with the Error Trigger node, and n8n runs it when an execution fails. Its error data includes execution.retryOf when the failed execution was itself a retry. n8n's docs note it cannot be tested with manual runs: it fires on production executions only.

The catch shows in the real run above. evt_0251 was parked through an error output, so the execution ended success. An error workflow would not have fired for it. Use both: the error output parks the events you expected to fail, and the error workflow catches the run that fails in a way you did not expect, such as the park step itself being unreachable. Alert from the list for the first, from the error workflow for the second.

Rung 1 shows the opposite blind spot. With no retry and no error output, evt_0101's run ended error with "The connection was aborted, perhaps the server is offline" and "timeout of 10000ms exceeded", while the customer had in fact been texted. An error workflow alert there would have been true and misleading: the run failed, the customer was fine. Red is not lost, as session 4 found 11 times on one day.

Real world

Keep the dead letters longer than the live ones. Amazon's SQS guide advises setting the dead-letter queue's retention longer than the source queue's. The reason applies to any automation: a parked event is only useful if it is still there when someone gets to it. If your list is a sheet that a cleanup Zap clears every night, or a store whose history is capped, an event parked on Friday may be gone by Monday. Check how long your list keeps things before the first outage, not during it.

Homework

Before session 6

30 min
  1. Sort every step of your own workflow into read, write with a key, or write with no key. Turn retries on for the first group, check the receiving API's docs for the second, and wire the third to a park step with no automatic retry.
  2. Read one provider's idempotency page for an app you write to. Write down three things: the header name, what a repeat returns (the first result, including a failure, or a fresh try), and how long keys are kept.
  3. Find where your tool keeps failed runs and for how long. n8n's executions list, Make's incomplete executions, Zapier's Zap history. If the answer is shorter than a long weekend, your dead-letter list needs to live somewhere else.
  4. Send yourself the alert from step 6 through the channel you would really use, and ask: could someone who has never seen the workflow act on it in five minutes? If not, add what is missing.
Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · A colleague adds an Idempotency-Key header to the send step, with the value set to a new random UUID generated inside that step. The duplicates continue. Why?

A key names one intended action. If the name changes on every attempt, there is nothing for the receiver to match. Take it from the event, which existed before the first try and travels with every retry and redrive.

2 · A workflow has an n8n Remove Duplicates node directly before the send. A send fails during an outage and the event is redriven that night. What happens, and what is the fix?

"Seen" was recorded at the wrong moment. Marking after success keeps a failed event eligible for its second chance, and the run log of the dropped redrive shows nothing wrong at all.

3 · What does a dead-letter queue give you that more retries cannot?

n8n's node retry tops out at 20 seconds and the bench's outage lasted 30 minutes. Only rung 4 texted all 344, by parking 13 events and redriving them. The redrive is safe only with the key, and the list is useful only if someone owns it.
